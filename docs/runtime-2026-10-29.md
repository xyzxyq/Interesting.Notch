# 2026-10-29 · CPU、进程能量和水滴/卡片动画实测

本轮针对当前工作区的 Release 构建测量。没有降低任何动画刷新频率，没有关闭用户的常驻动效作为最终优化。最终使用正常启动参数恢复应用；未发布或推送。

**后续勘误：** 同日真实选择题检查发现桥接漏答订阅重确认，导致 connected 状态下仍可能丢失任务。下述完整应用和独立桥接采样的 CPU、唤醒及进程能量计数仍是当时进程的实测值，但“桥接报告无任务”不能证明 Codex 真实空闲，不能将它们作为订阅恢复后完整工作负载的基线。隔离组件测量不依赖真实桥接。原因与修复验证见 [请求可靠性记录](request-reliability-2026-10-29.md)。

## 变更

1. 卡片展示前的固定等待从 32 ms 缩为 16 ms，保留初始布局提交机会与原有 0.5 秒展开曲线。原有展开中关闭、快速反向打开、忽略隐藏卡片和水滴等检查继续通过。
2. 卡片定位改为使用水滴底缘，包含多请求时水滴的体积变化；卡片上缘与静止水滴底缘间距为 6 点。呼吸及按压缩放会造成少量视觉间距变化，屏幕边缘仍需服从窗口可见范围。预览也遍历已挂载的锚点视图，复用真实点击的坐标转换，不再按屏幕顶部估算。最初固定锚点遗漏了约 23 点布局偏移，导致用户截图中的重叠；最终读回水滴底缘 y=824、卡片上缘 y=818。翻转/非翻转 NSView 与多请求体积均有回归断言。
3. 修复调试入口在强制终止主应用后遗留媒体流子进程的问题：先记录这些主进程拥有的媒体子进程，主应用退出后按命令再次确认并终止。保留独立 Codex bridge，不扫描或终止其他应用。另清理了历史与本轮测量累积的孤儿媒体流进程；它们几乎不使用 CPU，但持有资源。测试确认相关子进程退出、无关子进程保留、空列表在系统 Bash 下可运行。
4. Codex 开关改用 UserDefaults 的布尔读取接口，仍默认启用；支持原生启动参数提供的布尔字符串，使空闲诊断可以只通过本次进程参数完成，不改持久设置。

## 测量方法

- Apple M5、16 GB、macOS 27.0.1，内建 60 Hz 显示器；本轮在电池供电下采样。其他用户应用未冻结，系统调度及背景负载会影响短时结果。
- 完整应用每轮启动后等待 10 秒，采样 30 秒；CPU 以累计用户态/内核态时间差计算，100% 为一个逻辑核心。`proc_pid_rusage` 的 CPU 时间按本机 Mach timebase 换算，并与 `ps` 累计时间交叉核对。
- 读取 `rusage_info_v6.ri_energy_nj` 的增量，除以时间换算为平均 mW。**这是操作系统归因到该进程的能量计数，不是整机瓦数，也不能覆盖完整的 GPU、WindowServer、显示器及外部辅助进程能耗。**
- `powermetrics` 需要当前未提供的管理员认证；Xcode Power Profiler 明确报告不支持 macOS。这两个途径没有获得有效瓦数数据，不把它们写成成功测量。
- 表中 Codex 开关关闭及边缘装饰关闭均为诊断对照，随后恢复；不是最终产品改动。桥接状态在完整应用测量的起止均报告 connected、0 running、0 waiting，但后来发现订阅漏确认，未能据此验证 Codex 的真实任务状态；标签中的 active 文件名仅指正常启用。

## 完整应用结果

| 场景（每组 2 轮） | CPU 平均 | package idle wakeups/s | 进程归因能量折算平均功率 |
| --- | ---: | ---: | ---: |
| 常驻水波开启，Codex 启用，桥接报告无任务 | 4.21% | 45.80 | 4.87 mW |
| 常驻水波开启，Codex 暂时关闭 | 3.98% | 35.54 | 5.37 mW |
| 常驻边缘装饰暂时关闭，Codex 启用，桥接报告无任务 | 0.39% | 0.66 | 0.30 mW |

CPU 主要来自仍在可见运动的常驻边缘装饰；关闭 Codex 后的差异很小。装饰关闭对照只是定位开销来源，不代表最终版获得了约 90% 的降耗。最终版保留装饰、频率与内容。两次功率计数的波动也说明不能把小幅 CPU 差异直接换算成续航收益。

最终坐标修正重新构建后，又测量 30 秒：CPU **4.07%**、package idle wakeups **48.46/s**、进程归因功率 **4.41 mW**，与之前保留常驻装饰的结果接近。此时桥接同样报告没有任务，但 Codex 的真实运行/待处理状态未获独立验证。

## 动画与组件空闲

使用生产 SwiftUI 水滴、卡片、窗口生命周期代码构建 `-O` 隔离预览，无网络提交，不回答真实请求。临时源码只加入动画进度探针。测试期间保持可见并使用有期限的 ProcessInfo activity 排除 App Nap；这些探针和防节流逻辑不进入正式应用。

同条件前后各执行 7 次卡片展开/收起、7 次水滴出现/回收：

| 指标 | 调整前 | 调整后 |
| --- | ---: | ---: |
| 卡片触发至首次非初始进度更新，中位数 | 107.3 ms | 49.2 ms |
| 卡片展开，各次 P95 更新间隔的中位数 | 16.82 ms | 16.79 ms |
| 卡片收起，各次 P95 更新间隔的中位数 | 16.77 ms | 16.75 ms |
| 水滴主要运动段，各次 P95 更新间隔的中位数 | 16.77 ms | 16.73 ms |

这是一次前后短时对照，不能保证每次点击均减少 58 ms。应用侧探针衡量动画进度更新，不直接代表屏幕呈现 FPS；同一帧的重复布局调用按时间合并，水滴仅统计最初 650 ms 的主要运动，避免将弹簧极微小尾部及静止重复值当作掉帧。调整后水滴主要运动中仍有一次约 30.4 ms 的更新间隔，卡片展开/收起最大间隔约 23.8/23.6 ms，不宣称绝对无卡顿。

组件全部隐藏时 CPU 约 0.005%–0.019%，初始隐藏期间约 0.1–0.3 次 package idle wakeups/s，说明本次测试没有出现隐藏后的持续动画循环。水滴停留但仍有呼吸动效时约 3.38%–3.61% CPU；卡片与水滴同时停留约 4.84%–10.48%，短时波动较大，且不等于卡片本身的净开销。

一次未控制后台节流的复测出现定时动作合并、水滴直接跳到终态，其低 CPU 数据已排除，不能当作性能收益。最初的预览输出路径还遇到文件访问阻塞，改为临时目录后重测；该轮没有纳入比较。

单独使用 Instruments Animation Hitches 做屏幕呈现检查，避免它污染 CPU 对照。有效的初始 trace 记录 40 个约 16.67 ms 的 hitch；这说明仍有单个刷新周期级别的延迟，不能把应用侧 16.7 ms 更新间隔直接称为零掉帧。另一次记录只有 2 个 hitch，但水滴根本没有执行完整动画，已明确排除，不能宣称掉帧数下降。最终复核的应用侧记录确认水滴运动执行（303 个中间进度样本），但对应 Instruments 记录在目标退出后卡在保存阶段，已终止采集工具；不完整 trace 未纳入结果。缺少有效的最终呈现对照，因此不能宣称屏幕掉帧率改善。

独立 Codex bridge 的 25 秒采样约 0.24% CPU、0.04 次 package idle wakeups/s、0.59 mW 进程归因能量；未包含在主应用表中。后台几乎不活动的媒体流孤儿已清理，最终只保留当前主应用拥有的一个媒体流子进程，不据此声称 CPU 获得显著下降。

## 回归与证据边界

- 生产卡片生命周期回归包含早关闭、快速重开、忽略隐藏、答案有效性、默认启用/进程参数关闭，以及距底缘 6 点的定位断言。
- 实际点击预览水滴能够打开新版卡片；已有动效时序、能耗生命周期门控和媒体流检查复核结果记录在数据文件。
- Release 构建和本地签名通过。所有测试临时文件、逐次进度与 Instruments trace 位于可清理的 `build/runtime-20261029/`；[逐秒数据、测量摘要和源码哈希](runtime-2026-10-29-data.json) 已保留。
- 没有测长时间电池续航、外接多屏和不同刷新率；没有把关闭装饰的诊断结果作为保持原样动效的省电收益。
