# 专注播放、间奏动画与资源占用（2026-11-06）

## 行为

- 专注播放时保留专辑封面，封面右下角显示原有聚焦图标的 12 点徽标；右侧用累计专注时长替换持续频谱。岛体宽度、专注会话起点与分钟刷新节奏沿用 3.1.0。
- 无同步歌词或两句之间的间奏，在原歌词中心位置显示三个银白小光点。每轮 2.8 秒，三个点错开 0.18 秒轻微起伏；使用原生 Core Animation，最高 30 fps，不采集音频，也不增加 SwiftUI 逐帧计时器。减少动态效果时静态显示。
- 投影沿用外接电源、正在播放、屏幕未锁定、未休眠、非智能节能、岛体收起等条件。曲终不继续播放间奏动画；投影收起时销毁窗口内容和原生动画。

## 减少资源占用

歌词容器只在句子开始、结束、消散结束和曲终更新。空歌词不再保持 30 Hz 的 SwiftUI 时间轴；只有当前歌词与正在消散的上一句使用 30 Hz 动画。文字宽度在换句时测量，不逐帧调用 NSString 排版。玻璃投影固定为静态，取消阅读期间幅度很小的粒子闪烁；单道折射波、句末 0.4 秒粒子消散以及中性玻璃字形保持。减少动态效果和停止的播放时钟不会维持连续歌词帧刷新。

运行中 3.1.0 的 `sample` 报告在 `ImmersiveLyricLine.body` 中捕获到逐帧 `sizeWithAttributes`，并显示 SwiftUI 布局与 Core Animation 提交开销；报告保存在 `build/focus-efficiency-20261106/baseline-sample.txt`。

## 固定场景 CPU 对照

在同一台 Apple M5、同样的 640×110 点透明测试窗口、同一段歌词和同一个 Metal 库中，分别编译未修改的 3.1.0 组件与最终组件（`swiftc -O`）。每场景预热 3 秒，再用进程 `getrusage` 统计约 18 秒 CPU 时间；每个版本各运行两次，表中为两次均值。100% 表示占满一个 CPU 核心。测试进程隔离了播放器、桥接和整个岛体，不能代表整款应用或整机功耗。

| 场景 | 旧组件 CPU | 新组件 CPU | 相对减少 |
| --- | ---: | ---: | ---: |
| 持续歌词（粒子样式） | 11.75% | 8.22% | 30.1% |
| 无歌词 / 间奏 | 2.63% | 0.15% | 94.4% |
| 停止的歌词时钟（隔离组件） | 11.64% | 0.10% | 99.2% |

新组件的两次歌词 CPU 为 8.13%、8.31%；保留 30 Hz 折射波及句末消散。暂停场景仅验证组件的时钟停止能力，实际应用暂停后直接撤下投影，不显示静止歌词。第二次间奏样本期间读取过辅助功能树并截取组件窗口，因此包含观察开销；两次间奏原始值为 0.014% 与 0.280%，不应把极低读数当作稳定的精确功耗。原始样本和对照在 `build/focus-efficiency-20261106/{baseline,optimized}-run{1,2}.json` 及 `comparison.json`。

复现入口：`python3 scripts/check-focus-efficiency.py`；传入未修改源码目录即可运行旧组件。需要本机已安装的 3.1.0 `default.metallib`，使用同库是为了隔离此次 SwiftUI 调度改动。

## 封面恢复

真实复现：《没关系》/容祖儿/《小小》的 Apple Music 脚本封面为 0 字节，系统媒体流同曲提供 78,196 字符的 base64 图片。生产状态合并与解码路径恢复出 404×512 图片，验证未改变播放器状态。

专注独立控制器缺图时，允许系统媒体流补充同曲的图片和目录 ID；要求播放器、非空歌名/歌手/专辑相同，时长差不超过 3 秒，已有目录 ID 不冲突。独立播放器的暂停状态、时间锚点、进度与控制目标保持不变。不同来源、歌手、专辑、时长或目录 ID 的封面被拒绝。

迟到的目录 ID 会触发此前失败封面的补取；同曲成功封面短暂缺失时继续保留，且不重复发起目录请求。一个地区的目录/CDN请求失败后继续尝试备用地区；网络错误按原有任务加入一次 30 秒后的有限重试，换曲取消。未修改系统代理、目录匹配规则或额外引入图片供应商。

本机目录请求在系统代理路径出现超时，直接连接相同目录 URL 返回 200；这属于本机网络路径证据，不证明所有机器存在同一故障。原生同曲封面复用使本次复现不再依赖这个网络请求。原生和目录均无可用图片时仍无法恢复，不用其他版本或搜索排名猜图。
